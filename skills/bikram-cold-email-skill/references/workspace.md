# Skill Resources and Private Client Workspace

## Two locations, one source of truth each

- **Installed skill:** `bikram-cold-email-skill` (Bikram Cold Email Skill), containing instructions, `references/`, and blank JSON templates in `assets/`. Treat these resources as read-only. Resolve resource links from the installed skill, never from the current working directory.
- **Private client workspace:** a dedicated bot project with a `client-data/` directory containing the live `client-profile.json`, `campaigns.json`, and optional `sources/`. All unqualified runtime filenames in this skill refer to this private directory, not `assets/`.

Use one private bot project per client. A global skill installation may share instructions, never client state. If the host has not identified a stable private project, resolve it with the operator before saving; do not guess a directory from client names or document contents. Configure the host to use the same project across sessions.

## First use

1. Establish the client identity and the host's stable private project. Use an already configured private bot project without asking for its path again; if none is established, resolve it with the operator. Never infer a storage path from a client/company name or website. Explicit onboarding answers authorize saving those confirmed requirements locally, not MailWizz operations.
2. Inspect `client-data/` and both JSON paths before writing. Distinguish missing paths from access denied, unavailable tools, malformed JSON and known established history. Read/validate existing files; never replace them with templates. If a profile/register from an established bot is missing, or only one file exists without a known interrupted first-use operation, preserve what exists and use authorized recovery, not a silent reset.
3. For a genuinely new client with no existing records/history, keep `client-data/` excluded from version control, preserving existing ignore rules. With persistent file tools, **create the missing `client-data/` directory** using the available directory-create operation or equivalent before writing JSON. It belongs inside the private project, not inside installed skill files. A missing directory/profile is the normal first-use state, not a reason to refuse saving or ask the operator to create it manually.
4. Initialize missing [client-profile.json](../assets/client-profile.json) and [campaigns.json](../assets/campaigns.json) from the bundled templates using create-only writes. Bind both to one stable client ID, fill confirmed client/company/brand/requirements in the appropriate records, and leave unknowns null and campaigns empty. Never copy record templates into live arrays as if they were facts. The templates are document shapes, not JSON Schema validators.
5. Save incrementally as facts are confirmed; a missing meeting URL or unresolved optional service angle does not prevent saving the client, company, audience and CTA already supplied. Follow [client-workflow.md](client-workflow.md) for safe updates and revisions. Fresh-read both files and validate the saved facts and matching client IDs before saying they were saved. If creation partly fails, report the exact path/operation/error, preserve successful files and resume only the known interrupted initialization; do not overwrite or treat unknown partial records as new.
6. For the same client, add companies to the existing `companies` array and brands under their owning company, preserving stable IDs, siblings, defaults, sources/history and the campaign register. Do not create another client workspace or reset the profile for each company. Ask a scope question only when ownership/selection is ambiguous. Create `client-data/sources/` only when authorized materials are supplied; credentials stay in the host secret store.

Installation alone must not create client data, connect credentials or authorize a campaign. Once onboarding establishes identity/scope in the private project, perform the local initialization above without an unnecessary extra "may I create the folder?" question. If file tools or write permission really are unavailable, report that specific limitation and continue a local draft from supplied facts; do not claim persistence or label a merely missing path as unwritable. Never claim durable onboarding from chat history alone.

## Host boundaries

Restrict all client reads/writes to this private workspace; reject traversal, external absolute paths, and symlink escapes. Exclude data from Git and backups shared with other clients; `.gitignore` is not access control. Keep host permissions and MailWizz resource authorization client-scoped. Prompts and JSON alone cannot enforce isolation or approval.
