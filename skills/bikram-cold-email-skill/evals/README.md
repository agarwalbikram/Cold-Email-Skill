# Evaluations (1–57), file-backed scenarios (31–35), initialization regressions (45–47), writing regressions (48–50), and scope/picker regressions (51–57)

These manual, scenario-based evaluations are not an executable test suite or evidence of test/model results. `evals.json` is a case dataset: prompts, expected behavior, assertions, and fixture links; its presence does not mean any case was run or passed. An eval is an executed result only after an operator runs the scenario, inspects the resulting files/trace, and records a separate outcome. Cases 31–35 are file-backed scenarios described below; they deliberately pre-create client-data files and therefore do not cover first-use folder creation. Cases 45–47 cover first-use initialization with an absent directory, appending a second company to the same client, and permission-denied/established-record recovery distinctions; run 45 with persistent file tools in an empty private project and no pre-created client-data directory, then run 46 against the verified result in that same disposable project. Case 47 uses a simulated permission-denied tool response and must not modify storage. Cases 36–40 cover campaign reporting, missing metrics, reporting/change authorization, contextual copy review, and explicitly approved tracking changes. This skill covers cold-email writing, campaign setup, and requested campaign reporting—not infrastructure audits or DNS, header, seed-inbox, warmup, blacklist, or live deliverability checks. Those checks are not a launch gate. Reporting is read-only: show MCP-exposed status and opens/clicks/unsubscribes/bounces on request, with counts/rates/window/denominator when known; label unavailable metrics (not zero) and make evidence-qualified suggestions. Never change settings to obtain metrics; tracking changes require explicit approval and readback.

Cases 48–50 are offline/manual writing scenarios, not run results: 48 tests a first-pass wholesale-services draft grounded only in the supplied verified sender, service, FNAME, and website facts; 49 requests a subject-only improvement and requires the body to remain byte-for-byte unchanged with no saved preference; 50 explicitly requests the entire service suite and exact supplied longer subject, so the requested breadth/style overrides default concision. Cases 51–57 are offline/manual scope and interaction regressions, not run results. For saved draft cases, report save status briefly and truthfully; do not repeat file paths, field audits, or version details during ordinary edits, but keep failures, approval blockers, and full campaign-packet/version details visible when relevant. Case 51 isolates a one-off campaign CTA edit from profile preferences and unrelated register/history while allowing the selected campaign's required material-version/revision increment, revision-history entry, and stale-approval invalidation; 52 checks explicit future CTA persistence in one offer's existing cta_goal, required profile revision/timestamp/change-history bookkeeping, fresh-read reuse, and non-overwrite by a later one-off CTA (campaign register is empty to avoid approval-flag ambiguity); 53–54 require company-first scope resolution before copy, writes, or remote operations for ambiguous two-company email and campaign requests; case 54 preserves the existing separately authorized scoped remote draft-create path after selection, while requiring separate exact campaign/version approval for launch actions; 55 checks named-company and uniquely associated saved-campaign bypasses while allowing requested local draft saves; 56 checks duplicate-name stable IDs, fail-closed cancel/stale/unknown choices, and independent callback replay subcases after valid selection, cancellation, replacement request, and completion; callbacks are bound to the outstanding request/choice step, consumed on valid selection, invalidated on cancel/replacement/completion, and ignored even if the stable company ID still exists; 57 requires numbered choices when the host has no native picker and lists only companies actually present in its fixture. Use synthetic two-company fixtures with company-specific brands/offers and distinct scoped writing feedback, plus an unmatched company with no brands/offers; do not modify the existing two-brand fixture, which represents one company. Exercise each case independently in a fresh disposable workspace. Do not connect live MCP/remote services or send/schedule; case 54 may inspect the existing separately authorized draft-create path only through a simulated/sandboxed trace, never a live account. Dataset presence is not evidence of a pass. Record any observed outputs separately. Cases 41–42 cover framework selection without customer proof or recipient research, and permission-based affiliate copy that preserves price/disclosure while omitting unsupported story/testimony stages. Cases 43–44 cover contextual use of an operator-supplied service-led brand example: case 43 tests explanatory copy, two questions/asks serving one reply goal, verified [FNAME] mapping, a literal unknown brand token, and an informational website signature; case 44 checks that style is not treated as evidence or permanently saved and unsupported guarantees/testimonials are not copied. ## Isolation setup

Run only in a fresh, disposable project-local scratch workspace. For each individual scenario, make a new empty directory named `client-data/` under a dedicated scratch project inside the repository's ignored `.tmp/` directory (for example `.tmp/eval-31/client-data/`). Do not point the host at a real client project, shared workspace, installed skill `assets/`, or live MailWizz account. Confirm `.tmp/` is excluded from version control before putting files there. Do not enable MCP, remote integrations, scheduling, or sending; the synthetic operator identity is fixture-only and grants no real authority.

For each case, copy only its listed fixture files into the fresh `client-data/` directory, using this exact mapping:

| Fixture | Destination in scratch `client-data/` |
| --- | --- |
| `fixtures/onboarding-profile.json` | `client-profile.json` |
| `fixtures/empty-campaigns.json` | `campaigns.json` |
| `fixtures/two-brand-profile.json` | `client-profile.json` |
| `fixtures/two-brand-campaigns.json` | `campaigns.json` |
| `fixtures/price-correction-campaigns.json` | `campaigns.json` |
| `fixtures/approved-campaign-register.json` | `campaigns.json` |
| `fixtures/malformed-profile.txt` | `client-profile.json` (copy bytes exactly; keep the `.txt` source extension only in the eval fixture) |
| `fixtures/post-schedule-save-failure.txt` | Host evidence input only; do not install as client JSON |

The files in `files[]` are evidence/input links, not destination paths or instructions to overwrite a fixture in place. For case 33, copy `two-brand-profile.json` to `client-profile.json` and `price-correction-campaigns.json` to `campaigns.json`. For case 35, copy `approved-campaign-register.json` to `campaigns.json` and provide the host evidence file read-only to the simulated operator. The register contains the approved pending operation saved before the remote action; it does not claim that the post-schedule result was persisted. For case 34, preserve the malformed source bytes and compare the destination bytes to the fixture before and after. Never reuse a scratch directory between cases; never edit fixtures as part of scenario execution.

## Operator identity assumption

Prompts that say “verified operator” assume the isolated harness presents a synthetic identity reference, `fixture:verified-operator`, for test context only. It is not authentication, a credential, or production approval. No actual operator identity, client, account, MailWizz resource, or send authorization is represented. Case 35's host evidence is synthetic and does not authorize contacting a remote service.

## Scenario runs and observable checks

Execute each case independently by supplying its `prompt` and fixture inputs to the skill in an offline local-file harness. Record the response and observed file/host trace outside the fixture dataset as the run result. Do not infer successful writes from an assistant's statement: inspect the files.

- **31 — onboarding:** initialize from the profile fixture. Confirm the saved profile has a stable synthetic client ID/name and one confirmed company and brand, revision advances only after successful persistence, and unknown data remains null. Confirm `campaigns.json` still has `"campaigns": []`; approval remains required, standing send authorization false, tracking off. Trace contains no remote calls, send, or schedule.
- **32 — returning greeting:** initialize from the two-brand profile and register. Confirm response greets Cedar Lantern Studio and offers relevant returning-client actions without choosing Cedar Lantern or Cedar Lantern Home. Compare both files byte-for-byte before/after; trace shows fresh local reads only and no writes or remote calls.
- **33 — durable price correction:** initialize with the two-brand profile and the price-correction register. Confirm only `syn-offer-starter` changes from `$29/month` to `$39/month`; `syn-brand-cedar-home` and its `$49/month` sibling offer are unchanged. Check the change record includes timestamp, operator event reference, record ID, changed field, old/new values, reason and resulting profile revision. Check profile revision increments and a fresh process/read sees `$39/month`. The campaign register and remote trace remain unchanged; no remote sends/mutations.
- **34 — malformed profile:** copy the malformed `.txt` fixture bytes to `client-profile.json`. Confirm the response reports malformed JSON, the destination bytes/hash exactly match the pre-run copy, and no replacement, template reset, or write occurs. No campaign/register mutation or remote action.
- **35 — post-schedule save failure:** start from `approved-campaign-register.json` and supply the synthetic host evidence. Confirm the response reports UID `SYNTH-MW-UID-735`, the last observed scheduled state, and the failed local save; it must not claim a current remote readback or successful local persistence. With no connected reconciliation tool, leave the register unchanged, halt mutations, and request authorized readback before retry or recovery. Trace contains no duplicate create/schedule. The supplied host evidence is not a live readback.

The template-shaped JSON fixtures intentionally use reserved `.example` URLs and synthetic IDs/names. They contain no real client data or credentials. Keep test outputs and scratch data local and disposable; do not publish a run result as a dataset change.
